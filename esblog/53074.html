Git reflog 从本地记录到提交找回

差异审查回答“内容改了什么”，bisect回答“行为从哪里改变”，revert则用新提交修订旧修改。这次的问题是：刚才明明提交过一段笔记，切回 main 后却在当前日志里看不到，应该先去哪里找？

git reflog 提供一条本地线索：引用曾经指到哪里。把这条记录与提交祖先分开，才能理解“当前分支没有包含”与“对象已经不存在”之间的距离。

提交关系与引用记录是两条线

普通 git log main 沿 main 当前提交的父关系向前走；git reflog show HEAD 查看本地 HEAD 的位置更新。前者是在提交图中追溯祖先，后者是在这份仓库的引用记录中查找曾经的位置。git-reflog 官方手册还特别说明，HEAD 的引用日志会记录分支切换。

因此，同一个提交可以在 HEAD 的引用日志中出现多次：一次是提交产生的位置，一次是切换回来时的位置。条目数量不是新增提交数量，序号也不是提交在祖先链上的深度。

这次先分清三个对象

提交对象保存快照和父关系；main 等分支名保存当前指向；reflog 保存本地引用过去的更新。找回提交时，先找出对象身份，再给它一个新的分支名字。

本文使用普通、启用了引用日志的本地仓库。日志是否存在可先用 git reflog exists HEAD 核对其退出状态；git-branch 手册说明，非裸仓库通常默认启用引用日志。本文不讨论多工作树、子模块、服务端日志或已损坏的对象库。

gitrevisions 手册定义了序号形式：HEAD@{1} 查 HEAD 的前一个日志值，main@{1} 查 main 的前一个日志值。在本例中，一个得到 D，一个得到 A。它们都不能简单读成“当前提交的父提交”。

自检：HEAD@{1} 和 main@{1} 为什么可能完全不同？

两者查询不同引用的本地日志。HEAD 记录了脱离、提交与切回；main 在脱离期间仍停在 B。本例刚切回时，HEAD@{1} 为 D，main@{1} 为 A，不能用共同的序号推出相同对象。

这里没有修改 main、工作区或暂存区。把候选解析成完整 ID，也消除了后续引用更新造成的序号漂移：新的提交或切换会使 HEAD@{n} 的 n 改变，保存的对象身份却不会因为日志新增一行而改变。

  D --> E[检查父关系与文件内容]

创建成功后，HEAD 增加一条切换到救援分支的记录。本例新的 HEAD@{0} 为 D，新的 HEAD@{1} 变为 B。因此，若此时重新把 HEAD@{1} 当作原候选，就会选错。创建名字没有把 D 合并进 main；后续如何整合，应另行审查内容与提交关系。

  flowchart TD
  A[已核对完整提交ID] --> B{工作区与新名字符合条件}
  B -->|是| C[创建rescue-notes并切换]
  C --> D[新引用指向候选D]
  D --> E[检查快照与分支位置]
  B -->|否| F[先处理当前改动或另选名字]
自检：创建救援分支后，再运行原来的 HEAD@{1} 还会得到 D 吗？

本例不会。创建并切换分支又新增一条 HEAD 日志，HEAD@{1} 此时是 B。应使用已经核对并保存的完整提交 ID；救援分支指向 D，但 main 尚未包含 D。

序号和时间选择器都有本地上下文

时间形式如 main@{yesterday} 查询的是本地 main 在那个时刻的记录位置，不是筛选“昨天写成的全部提交”；筛选提交日期属于另一类问题。引用需要有相应日志，记录的时间、时区与保留范围也都影响可用结果。实际定位时，可以先用 git reflog show --date=iso HEAD 查看时间，再核对候选的完整 ID。

还要区分三个长得相近的表达式：HEAD@{1} 是 HEAD 日志的旧位置；main@{1} 是 main 日志的旧位置；在分支上省略引用名的 @{1} 查询当前分支日志，不能默认当成 HEAD 日志的同义写法。@{-1} 则属于之前切换过的分支或提交的选择语法，也不是“前一个提交”。这些区别由 gitrevisions统一定义。

找不到记录时，先问范围

现象 应先核对的问题
刚换机器或重新克隆 这是另一份本地日志，不会自动继承原机器的操作记录
提交在日志里，但对象无法读取 记录和对象可用性是两件事，不能把一行日志当作完整备份
查询某个很早的时间 该引用日志是否存在、时间是否明确、记录是否仍保留
文件从未被提交 reflog 不逐次记录编辑器里的未提交内容
创建分支失败 新名字是否占用，切换是否会影响当前未提交修改
想继续修改 main 先保留并审查候选，再决定后续整合，不把找到对象等同于完成整合

reflog 的记录保留受配置与维护影响，不能承诺任意旧位置永远可查。它是本地查找线索，而不是替代备份、协作分支或正式保存工作的约定。Pro Git 的数据恢复章节展示了先找到对象、再给对象增加引用的基本思路；本文改用脱离分支的独立练习，不需要制造破坏性操作来学习它。

资料与验证范围

原始资料核对于 2026-10-27：

  • git-reflog：本地引用记录、HEAD 的切换记录和只读查看。
  • gitrevisions：序号、时间、当前分支与先前切换选择器。
  • git-switch与git-branch：脱离状态、创建并切换、新引用与分支查询。
  • Pro Git：Revision Selection与Maintenance and Data Recovery：本地性、shell 引用与恢复思路。

tests/verify-git-reflog-article.cjs 在新建独立练习仓执行真实 Git，检查快照、父关系、引用日志、选择器漂移、时间选择和新分支可达性；工作区冲突与重名分支则验证拒绝后的内容和引用保持原状。所有教学仓保留，没有操作博客的部署仓，也没有清理任何目录。验证只说明这些受控历史中的命令语义，不保证任意已经缺失的对象或未提交内容都能找回。
